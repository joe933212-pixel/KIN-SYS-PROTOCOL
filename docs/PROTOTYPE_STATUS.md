## Current test scope

The transition tests exercise local state/history properties using SQLite. The tests do not establish arbitrary durability guarantees, full CEE recovery, distributed commitment, multi-institution trust, production readiness, novelty, or commercial superiority. Orderly close/reopen is not the same as power-loss or storage-controller failure.

## Payment lifecycle boundary experiment — 2026-10-22

- `protocol-reference/payment_lifecycle.py` separates an obligation record, stable payment instruction, provider acknowledgement, settlement evidence, and reconciliation finding.
- Additional integrity checks now reject reuse of an institutional operation ID when the actor, stage, rule version, consignment, or decision changes; payment settlement also refuses to finalize if the stored obligation amount/currency no longer matches the recorded payment. Payment settlement now also recomputes the stored payment request fingerprint before settlement, rejecting a payment record that has been relinked to a different obligation even when the alternative has the same amount and currency. A paired test exercises this corruption case against both the prototype and the conventional SQLite baseline. The inconsistent-obligation case is exercised against both the KIN-SYS lifecycle and an independently implemented conventional SQLite baseline; this is a parity test, not evidence of superiority.
- Instruction IDs are stable and request fingerprints reject conflicting reuse; the same instruction retry returns the existing local record rather than calling a provider. Provider acceptance does not mean settlement. Unknown outcomes remain unresolved; reconciliation does not submit payments. Settlement requires a reference and matching amount/currency.
- `protocol-reference/tests/test_payment_lifecycle.py` adds tests for instruction retry, one-instruction-per-obligation, acceptance-versus-settlement, unknown/reconciliation, mismatched settlement, settlement updates, duplicate settlement, ID conflicts, event conflicts, and file-backed reopen.
- The module is wired into `integrated_demo.py` for simulated confirmed, declined, and unknown outcomes. The integrated report includes a separate lifecycle trace and explicitly labels settlement as simulated. No live provider is called and no funds move. Local idempotency does not prove provider-side idempotency or prevent duplicate effects in a real distributed payment network.

## Interpretation

Even if tests pass, they establish only the local properties exercised. They do not establish cryptographic authentication, the full CEE lifecycle, comprehensive phase-by-phase crash recovery, concurrent multi-process correctness, distributed commitment, multi-institution trust, production readiness, novelty, or commercial superiority.

Next engineering gates: test more interruption points between every persisted stage and adapter, broaden corrupted/stale evidence paths and recovery across component boundaries; refine serialised adapter contracts; and arrange independent review. The new crash tests establish rollback after abrupt process exit at the injected pre-commit points only; they do not establish power-loss, storage-controller, or arbitrary filesystem durability. The current concurrency tests cover specific SQLite instruction/enqueue races only, not general concurrent multi-process correctness.
