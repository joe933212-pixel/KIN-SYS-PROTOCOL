## Overview

This milestone extends the provider-neutral, MINAH-first governed execution reference prototype into a broader institutional deployment, identity, authority and federation engineering baseline. It documents how independently governed KIN-SYS installations can establish local trust, exchange signed instructions and preserve separate decision authority.

This is a research and reference implementation release. It is not a production deployment, a legal assurance, or evidence that all institutional integrations are operational.

## Implemented reference capabilities

- **Institutional deployment domain model:** tenant-scoped institution, jurisdiction package, MINAH deployment and deployment-binding records; immutable version snapshots; lifecycle events; explicit validation and activation constraints.
- **Institutional lifecycle and authority:** authority-gated verification, review, approval, activation, suspension and revocation flows; version-pinned grants; replay-aware actor assertions; local HMAC reference profile and federated Ed25519 profile.
- **Institutional trust and grant provenance:** receiver-controlled issuer trust relationships and key status; issuer-signed grant envelopes; separate receiver acceptance; signed acceptance receipts; revalidation against receiver-local trust.
- **Provider-neutral identity boundary:** OIDC adapter and provider registry contracts, token/claim validation expectations, issuer/audience/nonce and assurance checks, tenant-local subject binding, bounded JWKS/HTTPS transport and key-rotation handling.
- **Cross-installation federation:** canonical signed instruction envelopes, receiver-side destination and trust verification, replay protection, durable PostgreSQL inbox/outbox state, leases/retries, signed receiver acknowledgements and sender-side receipt verification.
- **PostgreSQL persistence and tenant controls:** migrations and reference adapters for institutional registry, trust, federation inbox/outbox and related tenant-scoped records, with row-level security policies and fail-closed tenant-context checks.
- **Reproducible evidence:** local HTTP prototype smoke test, unit and integration suites, PostgreSQL-backed federation tests, paired comparison reports and integrated demonstrator reports generated by CI.

## Important limitations and assurance boundaries

- The local HTTP prototype remains a synthetic reference path. Identity, authority, legal rules, institutional evidence and payment interactions are not live production integrations; no real funds move.
- MINAH deployments and institutional governance adapters still require institution-owned integration, evaluation, evidence sources and operational controls. Registering an adapter is not proof of connectivity, conformance or legal authority.
- OIDC support is an adapter/reference boundary; no live national or commercial identity provider deployment is certified by this release.
- Signing and verification primitives do not establish legal competence, the legal force of a source, or the sufficiency of underlying approval evidence. Production key custody and institutional trust establishment remain deployment responsibilities.
- PostgreSQL-backed two-installation tests use separate database configurations but currently run both installation adapters in one operating-system process and share one CI PostgreSQL service. The process-separated mTLS transport test isolates transport with a minimal receiver stub; it is not a process-separated execution of both complete institutional runtimes.
- Independent hosts and database services, live end-to-end OIDC, full process-restart recovery across deployed institutional runtimes, and production operations remain outstanding validation gates.
- PostgreSQL row-level security is defense in depth. A custom tenant-context setting is not a security boundary against arbitrary SQL executed under the same database principal. Production deployments require least-privilege non-superuser roles, no `BYPASSRLS`, tightly controlled transaction-scoped tenant context, and trusted application authorization.
- The architecture does not claim exactly-once execution across CEE/IVM and network boundaries, distributed finality, or exactly-once external effects. Delivery and recovery remain dependent on receiver-side idempotency and durable reconciliation.
- The proposed production API surface and complete institutional onboarding experience are not all implemented. This release must not be represented as production-ready.

## Intended next engineering work

1. Run complete institutional runtimes in separate processes, with independently operated PostgreSQL services and institution-owned trust/key/identity configuration.
2. Validate the full receiver crash/restart interval after CEE/IVM commit and before durable inbox completion.
3. Integrate a real OIDC provider and production-grade key custody under institution-controlled policy.
4. Complete authenticated institutional onboarding, administration and operational interfaces.
5. Conduct independent threat-model review, penetration testing, tenant-isolation testing and deployment acceptance with participating institutions.
